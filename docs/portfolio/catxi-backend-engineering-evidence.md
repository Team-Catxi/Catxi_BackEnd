# Catxi 백엔드 엔지니어링 근거

이 문서는 프로젝트에서 실제로 측정하거나 코드와 구성으로 확인한 사례만 요약합니다. 결과는 [문서 색인](../README.md)과 각 실행 기록에서 재확인할 수 있습니다.

## 프로젝트 규모

가입자와 MAU 약 4,500명은 사용자 제공 값입니다. 피크 동시 접속이나 요청률을 나타내는 운영 계측은 아니므로 용량 계산의 입력값으로 쓰지 않았습니다.

## 이력서에 사용할 수 있는 주장

### 제한 자원에서 두 앱의 메시징 안정성 측정

두 앱 서버에 각각 1 CPU와 768 MiB를 제한하고 23개 사용자 쌍, 46개 WebSocket 연결로 5 SEND/s를 약 두 시간 유지했습니다. 35,995건을 전송했고 k6에서 상대 사용자 전달 성공률 100%, 전체 p95 335 ms, HTTP 실패와 dropped iteration 0을 관측했습니다. Hikari pending은 0이었고 Redis Stream lag와 DLQ도 관측되지 않았습니다.

이 수치는 로컬 Docker 실행입니다. AWS T3.micro의 CPU credit이나 실제 Firebase provider 호출을 검증한 결과가 아닙니다. 세부 조건과 시간 그래프는 [지속 부하 기록](../performance/sustained-load.md)에 있습니다.

### 가상 스레드와 플랫폼 스레드의 승자를 성급히 단정하지 않음

동일한 앱 이미지, CPU quota, reader 수, 부하를 두고 실행 순서를 바꿔 비교했습니다. 첫 비교는 가상 스레드가 더 잘 전달했지만 역순 반복에서는 플랫폼 스레드가 더 높은 성공률을 보였고 두 결과 모두 K6 기준을 통과하지 못했습니다. 두 모델에서 CPU throttling이 약 98%까지 관측됐고 Redis lag와 PEL도 실행 사이에 달랐습니다.

반복 결과가 뒤집힌 현재 근거로는 가상 스레드 우위를 주장하지 않습니다. CPU quota에 포화된 조건과 충분한 CPU headroom 조건을 나누고 현재 코드로 교차 반복해야 결론을 좁힐 수 있습니다. 상세 집계와 실제 Grafana 시계열은 [스레드 모델 비교](../performance/thread-model-comparison.md)에 있습니다.

별도의 0.20 CPU 후보 프로파일에서는 플랫폼 reader 1과 가상 reader 4를 각각 사용해 300초간 5 SEND/s를 보냈고, 둘 다 1,518건 전달을 관측했습니다. 종단간 p95는 각각 1,374 ms와 1,958 ms였지만 CPU 제한 주기는 양쪽 모두 거의 포화됐고 설정과 Redis backlog도 달랐습니다. runner manifest와 k6 summary JSON의 threshold 판정이 불일치하므로 이 수치는 threshold 통과 증거가 아닙니다. 모델별 설정 후보를 찾는 관측 결과이며 스레드 모델의 승자를 가리는 비교는 아닙니다.

### 마지막 방 자리를 데이터베이스 경합으로 검증

MySQL 8.0.36 Testcontainers에서 마지막 한 자리를 두고 4, 20, 64 동시 요청을 각 다섯 번 실행했습니다. 440회 시도 중 15회만 승인됐고 overbooking은 0건이었습니다. 동시도 64에서 p95 중앙값은 977.360 ms, Hikari pending 중앙값은 44로 올라가 동시성 안전성과 자원 대기 비용을 함께 확인했습니다.

초기 기록에 wave마다 다섯 명이 승인됐다고 적혀 있었으나 CSV 재집계 결과 각 wave에서 한 명만 승인됐습니다. 보정된 수치와 재현 제한은 [방 입장 정합성 기록](../performance/room-admission.md)에 있습니다.

## 수치 사용 전 확인할 한계

- 세 사례 모두 운영 AWS 트래픽을 대표하지 않습니다. 측정 환경과 트래픽 모델은 각 페이지에 명시했습니다.
- 2시간 부하에서 SQL Outbox `SENT`는 Redis 발행 상태이지 FCM provider 승인이나 단말 수신을 의미하지 않습니다.
- 부하 테스트 계정은 Firebase 기기 토큰을 사용하지 않았습니다. 실기기 전송 성공률은 아직 측정 근거가 없습니다.
- 방 입장 결과는 보존된 CSV로 검산할 수 있지만, 당시 동시성 harness는 현재 테스트 트리에 없어 현행 코드의 회귀 테스트로 소개하지 않습니다.
- 결과에 전후 대조가 없으면 개선률을 만들지 않습니다. 비교가 불완전하거나 방향이 반복에서 바뀌면 그 한계를 그대로 설명합니다.
